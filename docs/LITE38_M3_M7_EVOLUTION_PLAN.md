# Lite 38 双轨演化方案 · M3–M7

本方案从两份实际 M2 提交出发，以 M7 为终点。五轮沿用同一员工管理工作簿。下列案例是用于解释设计的合成样例，演化顺序由研究者设定。每轮的正式隐藏输入另行构造。

## 两份 M2 的实际起点

| 已有功能 | 实际位置与依赖 |
|---|---|
| 员工与离职档案 | `ActiveEmployees` 和 `SeparatedEmployeeArchive` 保存 ID、原部门与入离职日期。当前路径按员工记录读取单段任职，调动依赖档案 ID 能被识别。 |
| 永久调动与借调 | `DepartmentTransfers` 和 `TemporaryAssignments` 分别保存两类事件。借调覆盖借调期间的报表归属。永久调动仍改变借调结束后的归属。 |
| 员工查询与人数报表 | 员工部门查询在 `EmployeeRecordQuery!E19`，当前组织汇总在 `WorkforceStructureAnalysis!H25:I31`，月初和月末人数在 `MonthlyChangeQuery`。两份年报分别按横向与纵向布局呈现，通过三个既有工作簿级名称读取。 |
| 入离职统计 | `MonthlyChangeQuery!C6:I7` 仍从员工和离职档案的日期与源部门计数。全年趋势和图表另有计算路径。让员工能够重新入职会触及这些已有路径。 |
| 工资与成本汇总 | `HRCostAnalysis!C11` 根据月份，从月度整批成本数据查工资。`K11` 汇总原有成本分类。月度原表没有逐员费用明细，部门分摊需要新增可归属的成本输入。 |

第一份 M2 的人数计算在原有部门人数上调整调动与借调产生的增减，部分归属逻辑在 `AssignmentCalculations`。第二份在 `TransferHeadcountHelper` 计算各日期的个人归属，再由报表计数。五轮共用输入输出约定，保留两种实现方式。基线分数和源码事实见 [M2 实验报告](../experiments/lite38_temporary_assignment_m2/analysis.md)。

## M3 · 离职后重新入职

为同一员工 ID 增加多段任职。新增任职记录至少包含员工 ID、任职记录 ID、入职日、离职日和起始部门。原员工和档案行提供首段任职。员工查询支持通过 ID 和查询日期选择任职，原姓名查询默认仍按当天运行。任职间隔查不到有效部门，人数继续沿用原题的边界口径，即入职日之后、离职日之前计入。入离职统计记录每次真实入离职，另显示重新入职小计。永久调动和借调按同一 ID 加有效任职段匹配。上一段的调动与借调不能带入下一段。

**案例。** 林远原属研发部，曾正式调入科技部，4 月 12 日离职。6 月 3 日以同一 ID 在财务部重新入职，7 月借调到销售部。查 3 月应看到科技部，查 5 月无有效归属，6 月末在财务部，7 月末在销售部。人数从未重复计算，6 月的重新入职计入入职事件，7 月借调没有产生额外入离职。

**交互验证。** 用同一人跨三个日期重放查询、当前汇总与月年报，再检查旧档案没有被覆盖。只撤去重新入职记录时，新任职期间的借调归属和相关人数必须消失，原任职期间的结果保持。

## M4 · 部门合并与撤销

新增生效日期、源部门和继承部门，区分部门在业务事件发生时的归属与报表查询日的归属。合并可以串联，生效前保留原代码和统计，生效后归入当日有效的继承部门。现有七个报表标签作为历史口径保留，已经撤销的部门在其撤销后的统计中可以显示为零。用于记录入离职事件的分类按该事件发生时的组织版本确定。合并前已成立且仍在生效的借调随接收部门迁移。生效后新填入的事件须引用有效部门。无继承部门的撤销只接受无人归属且无未完借调的部门，部门合并关系不得成环。

**案例。** 林远 7 月仍借调至销售。7 月 15 日销售并入科技，7 月 25 日财务并入行政。7 月初他计入销售，7 月末计入科技。借调结束后，他回归最新的有效永久部门行政。6 月的入职事件仍记在当时的财务部，部门合并本身不产生入离职事件。

**交互验证。** 在同一份工作簿中测试合并前后、串联合并、在途借调以及新登记误用撤销部门。只改变一条合并的生效日，相关月份的归属随之改变，较早月份保持。公司人数守恒。

## M5 · 人力成本分摊

第一版选择工资作为分摊对象。新增逐员的月份、费用与完整覆盖月份清单，覆盖月份的 `HRCostAnalysis` 工资汇总和部门分摊读取同一份工资明细。原有月份和其他成本分类沿用已有口径。以员工当月参与计算的任职日为分摊范围。每天采用 M1–M4 已确立的归属，含借调覆盖、任职间隔和部门合并。金额按最小货币单位分配，整数商分给每个有效日，余数按日期从早到晚分发。无有效任职日的费用进入待核查状态。部门合计应等于有效工资明细合计。月末部门和当月成本归属可以不同。

**案例。** 林远 5 月整月在职，工资 3,100 元。5 月 11 日至 20 日借调到销售，销售在 16 日并入科技，18 日发生原永久部门研发到财务的正式调动。研发、销售、科技、财务分别分摊 1,000、500、500、1,100 元，月末只在财务计一人。只推迟合并日期会改变销售与科技的工资分摊。

**交互验证。** 隐藏输入覆盖同月离职后再入职、借调跨月、合并和借调边界重合、分摊余数。核查逐部门金额、总额守恒和原成本页面。单独改变任职、借调或合并的一项输入，检查对应金额随之改变。

## M6 · 部门预算与人员编制控制

增加按有效部门和月份登记的编制、工资预算，以及新调动和借调的待审批申请。已有 M1、M2 台账代表已授权事件。申请按有效日和稳定顺序审查，用现有归属及分摊逻辑计算接受申请后的用人和工资。在有限的预算规划月份内，检查受影响月份的逐日编制峰值和工资总额，等于上限可以通过。通过的事件进入同一归属与成本计算，后续申请会看到前面已占用的额度。被拒事件保留判断和原因，其业务效果不进入报表。撤销部门的申请按 M4 的有效部门规则处理。两组均可用公式或在工作簿支持范围内组织等效的计算结构。

**案例。** 某部门 6 月最多容纳三人，工资预算 7,000 元。现有一人占用 4,500 元。接受第一项借调后为两人、6,500 元。第二项申请加入后是三人、7,700 元，因此被拒。最终人数和工资仍为两人、6,500 元。把首项申请改成更低费用，第二项可获批准。另设预算充足、编制超限的用例。

**交互验证。** 对照同一申请单独处理与接在已批准申请之后处理的结果。读取审批输出、月年报和成本表。保持申请记录不变，只改借调日期或已有成本，仍能触发相应的不同审批结果。验证已授权历史记录不会因事后调低预算被删除。

## M7 · 历史追溯更正与已签发报告

为可更正的任职、调动、借调、组织和费用记录建立稳定事件 ID。更正以记录 ID、版本顺序和替换值或作废操作追加，原始记录保留。实时和历史重算使用当前可见的有效版本。已有报表提供两种读取方式：按期间读取重算结果，按签发编号读取当时的固定值与版本。更正引发不合法的后续事件时，保留该事件及错误原因并标记待复核，阻止它进入有效业务计算。已签发的审批仍保留原决定，新的违规状态进入当前风险提示并影响今后的审批。更正目标互相矛盾或不存在时明确报错。

**案例。** 7 月报表和审批已签发。后来发现一条借调应在 7 月 16 日结束，原记录填为 7 月 21 日。同一工作簿的重算版应缩短借调期间在接收部门的工资分摊，重新给出有关日期的归属和部门预算余量。若随后出现新申请，应使用更正后的余量。已签发的 7 月报表和审批仍保留原时点结果。另设任职日期更正使后续调动无效的用例，检查有关联的状态告警。

**实际状态验证。** 先用提交工作簿和第一批输入计算，再由统一的发布步骤把真实输出写成值快照，并保存版本和内容指纹。继续在同一副本追加更正、重算、处理下一次申请。检查重算与新审批对照 GT，并通过工作簿自己的签发查询接口重新读出原报告。快照本身和正式查询结果都须与发布时逐项相同。如果初次发布就算错，单独记作发布内容错误，仍检验快照是否被篡改。整个流程使用模型实际产生的状态。

## 如何确认耦合增加

比较单位是可单独调用或改变输入来核查的业务行为，例如员工查询、历史人数、入离职事件、工资归属、审批决定和报告签发。先给业务功能和输出路径建立固定 ID，每轮报告三类事实：新规则必须改变哪些既有行为，哪些既有输出仅被读取，以及单独改变某项上游证据时哪些可观察结果必须变化。单元格数、公式数和同一条件重复次数各自记录。

| 轮次 | 本轮新增的可检验依赖 |
|---|---|
| M3 | 同一人在不同任职段的有效性决定调动、借调和入离职计数 |
| M4 | 组织版本同时改变任职、调动和借调产生的部门归属 |
| M5 | 薪资值与前三轮的同一套按日归属结合，产生成本分摊 |
| M6 | 人数和成本共同约束审批，已通过的审批反过来影响下一申请的业务状态 |
| M7 | 历史版本变化触发上述链条重算，同时受已签发状态约束 |

每轮在参考实现上选至少两类新旧功能共存的输入，并做成对干预。用一处事实或事件差异验证新增依赖的下游效果。要是声称必经的环节被移除后输出仍然可以正确得到，把该环节标记为未验证，重新核对设计后再冻结。报告实际触及的既有功能数、依赖路径数、可区分的交互案例数和各项测试变化。预计的依赖面在设计中扩大，实测是否扩大由这些证据决定。

## 两条轨迹的执行与终点

1. 两条轨迹分别继承各自上一轮实际交付的工作簿。可重算的失败提交也继续继承。无可用提交时标记该轨迹中断，保留失败产物和原因。两条轨迹使用同一题面、模型设置、公开输入输出接口与隐藏 GT。题面说明业务规则及接口，查找受影响公式和辅助表由模型完成。
2. 每轮先核验参考文件和两份真实起点，验证新功能确实缺失，并建立旧功能起点分。题面、接口、测试数据、GT、评分器和重算环境版本在启动该轮模型前冻结。先确认隔离会话内的工作簿自检能运行，并确认外部正式重算。报告按业务名称读取各实现的接口，检测器不以单元格布局或公式写法判断业务结果。
3. 提交后复测 M1 至当轮所有仍适用的功能。原规则继续适用的场景照原 GT 复测。被明确升级的新语义同时增加新输入和版本对应的 GT。逐项记录新功能缺失、功能交互错误、旧功能由通过变失败、旧缺陷延续或修复。区分业务错误、接口问题和环境故障，保留冻结原判与独立复核。记录运行标识、起点和提交哈希、轨迹、执行时间与测试版本。
4. M7 之后汇总两条轨迹。如果没有观察到可核实、值得追查的业务遗漏、功能交互错误或回归，停止沿这条人工加复杂度的路线继续加轮。下一步转向验证真实成熟工作空间的任务来源、不同文件各自承担的业务职责，以及能否自动构建足量的可验证案例。两条轨迹作为探索性证据。
