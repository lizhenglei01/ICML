# Approve movements against department staffing and payroll limits

Add two visible input sheets. `DepartmentLimits` has the headers `Month`, `Department`, `Headcount Limit`, `Salary Budget`. `Month` is the first day of one planning month per batch. Each listed active department has one limit row. `MovementRequests` has these headers in A:I: `Request ID`, `Kind`, `Employee ID`, `Start Date`, `End Date`, `From Department`, `To Department`, `Decision`, `Reason`. The first seven columns are inputs. `Kind` is either `Transfer` or `Assignment`. A permanent transfer has a blank end date. A temporary assignment has the same date semantics as the existing temporary assignment ledger and a blank from department. The request dates start in the planning month. Evaluate up to 20 input rows in order of effective date, using row order for ties. Test inputs use a distinct applicant per batch row and chronologically valid employment histories. Leave both input ledgers blank on delivery.

Use the existing employment, organization, movement and payroll behavior to compute the proposed change against the planned month. All inputs in the existing M1 and M2 movement ledgers are authorized and remain in force. Compare payroll for the planning month and daily staffing during that month after adding the proposal and any earlier approved requests. Use the existing daily payroll allocation and department rules, including nonoverlapping assignment dates and permanent transfer precedence. The limits in the sheet apply only to their listed departments. Check a limit when the proposal increases that measure for the department. Equality with the limit is allowed. A transfer must use the permanent origin on its effective date. A proposed movement that starts outside employment or references an inactive department must be rejected.

Write `APPROVED` with an empty reason when accepted and `REJECTED` with one reason otherwise. Reasons, in priority order, are `EMPLOYMENT`, `DEPARTMENT`, `CAPACITY`, `BUDGET`. Unsupported and mutually conflicting existing assignments are outside the tested valid input scope. A rejected proposal has no effect on results. An approved proposal enters the same effective view as other movements. Employee lookups, current and historical headcounts and payroll must reflect approved movements, including subsequent months. A later request must have access to the capacity and payroll left by earlier approved requests. Existing ledgers and previous reports remain usable. Return a recalculating XLSX.
